### 1-Q2 ｜ 维度：框架 ｜ [R-01] [R-07]

**面试官**：你提到用 Spring AOP + 自定义注解实现操作日志、替代原有人工登记、日志覆盖率 100%。先说清 AOP 的生效链路：切面是怎么织入到目标方法上的，哪些调用路径下会失效？

**候选人**：结论先行：Spring AOP 是运行期代理织入，不是字节码改方法。Bean 初始化后由 AbstractAutoProxyCreator 判断是否需要代理，命中就包成 JDK 动态代理或 CGLIB 子类，调用方拿到的是代理对象；调用进入 MethodInterceptor，再按自定义注解匹配，环绕执行时写操作日志。失效路径：类内部 this 自调用不走代理、private/static 方法不代理、不是 Spring 管理的对象、以及跨进程调用。取舍上代理方式的代价是每次调用多一层间接和一次注解匹配，但换来了业务代码零侵入，替代人工登记。

**追问 1（面试官）**：100% 这个数字的分子、分母分别是什么？统计周期多长，数据是怎么取出来的？

**追问 1（候选人）**：这个我记不准口径，不猜。我的理解它应该是「接入了注解的对外操作入口数 ÷ 该模块应记录日志的接口总数」，但我没有回查过当时的统计源，也说不出统计周期和取数方式。简历里只留下了 100% 这个数，分子分母我当时没留档，这是我的问题。

**追问 2（面试官）**：同一个类内部方法自调用，或者通过 Dubbo 跨进程调用时，你的切面还能生效吗？失效了怎么发现、怎么补救？

### 1-Q3 ｜ 维度：通用

**面试官**：出库单列表接口从 5 表联查拆成两段查询 + 批量填充，P99 从 1.8 秒降到 320 毫秒。先讲清原来那 5 表联查的执行计划长什么样，时间主要花在哪一步？

**候选人**：结论先行：瓶颈不在 SQL 写法，而在被驱动表没有合适索引导致回表与 join buffer 放大。原来 5 表联查是出库单主表驱动，再关联订单、商品、仓库库位、面单等表，驱动表逐行去被驱动表找匹配，部分表走的是全表扫描或 Using join buffer 的块嵌套循环，行数被放大，时间主要花在回表和扫描上。改成两段：先单表查出本页出库单主数据，再用批量填充按 ID 一次捞出关联信息，把 N 次点查压成少数几次批量查。具体的 EXPLAIN 输出我当时没留档，记得不是很精确。

**追问 1（面试官）**：320 毫秒这个数是怎么测出来的？样本量、统计窗口，以及当时单表数据量和并发是多少？

**追问 1（候选人）**：能确认的口径只有两个：统计窗口 7 天，数据取自 SkyWalking 埋点，这是简历里写明的。320 毫秒是这段时间的 P99。样本量、当时单表数据量和并发，简历里没有记录，我当时也没留档，我记不准，不编一个数给你。

**追问 2（面试官）**：改成两段查询后，IN 条件里一次最多塞多少个 ID？如果这次命中 5000 条出库单，批量填充这一步会怎么退化？

**追问 2（候选人）**：具体批大小我记不准，需要回查代码，我不给一个假数。方向上一定是分批，因为 IN 列表过长会让优化器放弃索引，改成 range 甚至全表扫。5000 条的退化点很清楚：批量填充返回的行数会被关联表放大，内存占用和网络包变大，甚至把原查询打回全表扫描，这时应该按主键区间分页填，而不是一次拉全。

**追问 3（面试官）**：这套优化在单表涨到亿级之后还有效吗？索引和查询形态你会怎么调整？

**追问 3（候选人）**：两段查询这个形态本身还成立，但亿级单表要配套改：用覆盖索引把批量填充的回表去掉，主键用有序区间替代大 IN，再配合历史数据归档或按时间分区。再往上就是分库分表，但这块我只在测试环境做过 ShardingSphere 验证、没上生产，TiDB 也只是了解过、没实际使用，这是我的明确边界。

### 1-Q4 ｜ 维度：中间件 ｜ [R-05] [R-06]

**面试官**：你用 RocketMQ 事务消息保证「订单下发 → 库存扣减」的最终一致，累计处理 1.2 亿条消息。先讲清消息从生产到消费的完整链路，以及本地事务回查是在什么条件下触发的。

**候选人**：结论先行：事务消息保证的是本地事务与消息发送的原子性，不是端到端的强一致。链路是：生产者先发 half 消息到 Broker，Broker 落盘成功后应答，生产者才执行本地事务，然后回传 commit 或 rollback；commit 的消息才可见并投递给消费端。回查的触发条件是本地事务结果未决——生产者返回 UNKNOWN，或 Broker 在超时时间内没收到 commit/rollback，就会回查生产者询问本地事务状态。消费端拉取、扣库存、再 ack，失败按重试策略重投，重试耗尽进死信队列，走人工补偿入口。

**追问 1（面试官）**：1.2 亿这个累计量的分子、分母是什么？按什么周期统计，重试消息和死信消息算不算在内？简历里的 3 个 Topic 分别承载什么业务，这个 3 的分母又是什么？

**追问 1（候选人）**：两点要更正。第一，1.2 亿的口径简历里只写了「累计处理消息 1.2 亿条」，分子分母、统计周期、是否含重试和死信，简历没有记录，我也记不准，不猜。第二，这里有个口径错位：简历里的「3 个 Topic」是挂在 Kafka 后面的，原文是 RocketMQ、Kafka（3 个 Topic 的生产与消费），所以 3 个 Topic 的分母是 Kafka 侧，不是 RocketMQ；我没写过 RocketMQ 有几个 Topic。

**追问 2（面试官）**：消费端幂等靠什么实现？如果库存扣减成功但回执丢失，消息重投之后你靠什么判断这条已经处理过？

**追问 2（候选人）**：先示弱：幂等的具体实现简历里没写，我记不准，不编。你假设的「扣减成功但回执丢失」这个场景，我也不能声称处理过。我的理解是通用做法对业务唯一键建唯一索引或去重表，重投时靠唯一键冲突判定已处理——但落到我们项目是哪一种，我没把握。

**追问 3（面试官）**：如果这套链路要跨库、甚至换成 TiDB 这类分布式数据库，事务消息这套机制还成立吗？你简历里写了分库分表只在测试环境验证过、TiDB 只是了解，那这条链路真上分布式数据库，你的盲区在哪？

**追问 3（候选人）**：事务消息的 half 消息本身在 RocketMQ，本地事务指的是业务库那一侧，所以单库换 TiDB，机制形式上还成立。但跨库时就断了：一个本地事务覆盖不了两个数据源，回查语义也对不上，得改用本地消息表加对账这类补偿。我的盲区很明确——分库分表只在测试环境做过 ShardingSphere 验证、未上生产，TiDB 只是分享里了解，没有生产运维经验。
