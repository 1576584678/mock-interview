## 三、核心准则（违反即视为演练失败）

1. **只用上面的事实作答。** 简历没写、代码里没有的经历，一律不能说。
2. **不确定时必须示弱，不许猜。** 正确姿态：
   > "这块我只在设计层面考虑过，没有生产落地经验。我的理解是……如果要我用，我会先验证……"
   错误姿态：编一个听起来合理的机制。
3. **数字必须带口径。** 说百分比时主动给分子分母。
   > ❌ "准确率 99.98%"
   > ✅ "对账一致率 99.98%，口径是日终对账中一致行数除以比对总行数"
4. **超出能力边界时诚实。** 例如没有 RocketMQ / TiDB / MyCAT / WMS 作业侧经验——直接说，
   并给相邻能力做迁移论证，**绝不编造**。
5. **被指出错误时**：承认 → 更正 → 给出正确版本 → 一句话收尾。不辩解、不找借口。
6. **答案结构**：结论先行 → 机制 → 取舍 → 边界。主答 80–150 字，追问回答 40–100 字（口语长度）。

## 四、本轮问题（**请逐题作答，并逐层回答面试官的追问链**）

```
### Q1｜维度：分布式数据库
问题：上一轮你把跨库一致性落在了「本地消息表 + 日终对账」上，但对账这半句你只说了它存在，没说它怎么跑。现在按落地问：出库单库和库存库之间的对账体系，你打算怎么设计？先讲清三件事——对账的分母是哪些数据（当天全部出库单，还是只有走过消息的那部分）、比对键用什么（出库单号还是别的业务唯一键）、差异出来后你按什么分类、按什么顺序处理。
面试官准备的追问链（请**逐层**回答，共 3 层）：
  1. 机制层：这个对账任务怎么跑才不打爆线上——是全量拉两个库，还是按时间片分桶拉？如果出库单库一天 300 万单，这个对账要跑多久、占多少资源，跑在什么时间窗？
  2. 取舍层：实时对账（消费端每条都回查）和日终对账你排掉哪一个？说出你排掉的那个方案落在出库链路上的具体代价，不要只说「实时性差」。
  3. 极端层：如果某笔单据在出库单库被业务改成「已取消」、库存库侧扣减已经发生，而对账只比状态字段，这种漏账你怎么设计才能发现？先查哪张表、看哪个字段？

### Q2｜维度：框架　目标风险：R-07
问题：换到你简历里写了、但前两轮我一直没追问的那块：出库单创建要同步调库存、波次、面单这几个下游，你用 Dubbo 或 HTTP 发起的远程调用一旦超时重试，出库链路上会出现什么后果？先说清这套调用的超时、重试次数、重试对象是怎么配的，配在框架侧还是业务侧。
面试官准备的追问链（请**逐层**回答，共 3 层）：
  1. 机制层：这套超时重试在什么情况下会失效——比如业务唯一键在两处上游各自生成、或者下游自身也在重试时，你的幂等还成立吗？失效后你怎么发现？
  2. 现象层：调用失败你靠什么先看到——接口错误率、Dubbo 的超时统计，还是下游对账出的差异？从出事到被发现大概多久，谁来看？
  3. 极端层：如果重试请求落到了另一个下游实例、而它读的是有 200 毫秒主从延迟的从库，你会看到什么现象，怎么把它和真正的重复扣减区分开？

### Q3｜维度：中间件
问题：把你简历里最大的那个数字坐实：「基于 RocketMQ 事务消息保证订单下发 → 库存扣减最终一致，累计处理消息 1.2 亿条」。先只给这个 1.2 亿条的口径：分子是什么（生产条数、消费条数，还是两者相加）、分母是什么（一条业务链路对应 1 条消息还是多条）、统计周期多长、重投与死信重投的那部分算不算在内。
面试官准备的追问链（请**逐层**回答，共 3 层）：
  1. 口径层：前两轮你如实说过 Kafka「3 个 Topic」和「人工补偿入口日均 30 余笔」的口径你记不准。那 1.2 亿条这个数你现在的把握有几分？如果要用「95%」这类比例去描述这条链路的消费成功率或补偿成功率，你的分子、分母分别是什么——拿不出来你打算怎么补这个口径？
  2. 机制层：「不丢」和「不重」分别由哪个环节保证——生产端、Broker、消费端各承担哪一段？哪一段你们其实没保证、只是靠对账兜底？
  3. 极端层：如果消费端已经 ack、应用进程随即被 K8s 杀掉，重启后这条消息会被重投还是就此丢失？你从哪个指标或哪条日志能判断出来？

### Q4｜维度：业务场景
问题：回到你的主战场：出库单创建之后就是波次分配。请讲清你们的波次是按什么规则聚单的——按仓库、按承运商、按时效、还是按拣货路径？先说你实际用的规则和它的上限，再说这个规则是谁定的、定的时候依据什么。
面试官准备的追问链（请**逐层**回答，共 3 层）：
  1. 现象层：一个波次最多聚多少单、等多久会被强制拆掉？这两个阈值你们实际是多少，改过几次，每次为什么改？
  2. 机制层：如果波次里某件商品缺货、或者某张面单打印失败，同波的其他单是继续走还是整波回退？你们的真实做法是哪一种，代价是什么？
  3. 取舍层：按拣货路径聚单能提拣货效率，但会让单量小的仓库拆出大量小波次，你怎么平衡？说出你选的那一边的代价。

### Q5｜维度：通用
问题：最后一个问题问边界，不追技术细节：你简历里明确写了分库分表只在测试环境做过 ShardingSphere 验证、TiDB 只是技术分享里了解过、JVM 层没有独立排查过、真故障演练也没做过。假设你入职后第一个季度就被安排去主导一次出库单表的分库分表迁移，你凭什么让团队相信你能接住？请给出你前两周的具体动作。
面试官准备的追问链（请**逐层**回答，共 3 层）：
  1. 边界层：你前两轮多次出现「这块我记不准，不编」，这是好习惯。那请举一个你确实没把握、但当时仍被要求当场给结论的真实场景：你最后是怎么处理的，结果如何？
  2. 转岗层：你 2019 到 2021 在电商后台做订单、售后，2021 转到仓储履约出库。这次转岗你当时补了什么、用了多久才能独立接线上问题定位？现在回头看，哪块补得最不到位？
  3. 收尾层：如果这次面试没通过，你希望我们反馈的是哪一类问题——数字口径、机制细节，还是项目深度？为什么是这一类？

```

      ]

约束：
- `items` 必须覆盖第四节的**每一道题**（qid 一一对应），**不要漏题**；
- 每题的 `followups` 必须把该题的追问链**全部**回答（最多 3 层），`question` 照抄追问原文；
- `candidate_questions` 是结尾反问环节的 2–3 个问题，要体现对岗位/团队技术现状/个人成长的思考。

写完后**只回复 3 行以内的摘要**（轮次、题数、有无示弱项），不要把 JSON 全文回给调用方。
