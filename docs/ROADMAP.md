## P1 · 解析层

**产出**：`pipeline/parse_resume.py`、`pipeline/parse_jd.py`

**功能**
- 简历：pdf / docx / md / txt → `resume.json`（基本信息、技能、经历、项目、量化声明清单、机制声明清单、时间线）
- JD：文本 → `jd.json`（硬性要求、加分项、能力维度、业务场景、薪资区间、隐藏痛点）

**DoD**
- [x] 4 种简历格式全部解析成功，中文不乱码（md / docx / pdf / txt）
- [x] 量化声明与机制声明被单独抽成清单（供 P4 验真）
- [x] 时间线自动抽取并能检出空窗（真实简历检出 2 段：4 个月、2 个月）
- [x] PDF 解析失败时自动降级且不中断（pdftotext → LibreOffice → 内置解析 → 明确报错）
- [x] 解析结果经人工抽检，字段准确率 ≥ 95%（fixture md / docx / 真实 PDF / 真实 JD 四份输入）

**回归测试**：`python tests/run_tests.py` → **49 项通过 / 0 失败**（含真实 PDF，需设 `MOCK_INTERVIEW_TEST_PDF`）

**P1 踩过的坑（已修，留作教训）**

| 现象 | 根因 | 修法 |
|---|---|---|
| 章节一个都识别不到 | 续行合并未检查「上一行是标题」，标题被下一行吸走 | `should_merge` 增加 `is_heading(prev)` 守卫 |
| 「项目经历 · 商业项目」被当正文 | `is_heading` 允许前缀匹配而 `section_of` 只认精确匹配 | 两者统一前缀匹配口径 |
| 技能只认出 3 组 | 技能段是「类别行 + 内容行」两行式，通用合并把类别吸进上一行 | 技能段禁用通用合并，改用 `merge_skills_lines`（只并 1–3 字碎片）|
| 「AI 工程」被拆成 `AI` + `工程` | 空格式类别匹配把标签内空格当分隔符 | 空格式要求后半段 ≥ 6 字 |
| 项目被炸成 120 条 | PDF 无列表符号，短行全被当项目标题 | 只认含平台/系统/中台…关键词且无标点的短行 |
| 姓名抓成「设计」 | 姓名行与标题行被合并 | 合并规则收紧为「上一行以空格收尾 / 本行 ≤2 字 / 上一行 ≥34 字」|

**P2 期间回补的 P1 缺陷**（JD 解析丢需求，属严重级别，必须回补）

| 现象 | 根因 | 修法 |
|---|---|---|
| 「有限流、降级、熔断的实践经验」**整条需求丢失** | 行既不匹配 `NICE_RE` 也不匹配 `MUST_RE` 就被静默丢弃 | 改为按章节（岗位职责 / 任职要求 / 加分项）归类，并保证零丢失：未归类行并入硬性要求并告警 |
| 「5 年以上 Java 开发经验」变成「年以上…」 | `split_lines` 用贪婪字符类剥行首，把行首数字一起吃掉了 | 只剥列表符号与 `1.` / `1、` 编号 |
| 「岗位职责：」被当招聘元数据跳过，职责段错位进硬性要求 | 元数据过滤排在章节识别之前 | 章节识别优先于元数据过滤 |
| claims 里出现「99.98%。」这种孤立碎片 | PDF 恰好在数字前断行 | 短数字句并回上一句 |

## P2 · 演练层 ✅

**产出**：`pipeline/orchestrate.py`、`pipeline/risks.py`、`prompts/interviewer.md`（实装）、`prompts/candidate.md`（实装）、`rounds/`（状态与每轮记录）

**职责边界（关键设计）**
编排脚本**不调用模型**，只做四件事：渲染指令 → 校验契约 → 落盘状态 → 校验 DoD。
模型调用由宿主 agent 完成。这样整层可回归测试、可重放，也能挂到任何 agent 框架上。

| 命令 | 作用 |
|---|---|
| `init` | 播种风险点（R-01…）+ 按轮次切分维度与风险 → `rounds/state.json`、`out/risks.json` |
| `prepare --round N` | 渲染 `rounds/round-N.interviewer.md`（注入 JD / 简历 / 风险点 / 上一轮问答 / 已问题目）|
| `prepare-candidate --round N` | 校验出题 JSON 后渲染 `rounds/round-N.candidate.md`（注入问题与追问链）|
| `commit --round N` | 契约校验 + 合并出题与答题 → `rounds/round-N.json`，更新覆盖状态 |
| `check` | DoD 校验：维度全覆盖 / 每条风险点至少被追问 1 次 / 调用 ≤60 / 墙钟 ≤15 分钟 |
| `status` | 状态快照 |

**由脚本强制（不靠 agent 自觉）的约束**
- **编号稳定**：P2 的追问目标与 P3 的风险报告共用同一批 `R-xx`，编号引用闭环才有物理基础。
- **契约不满足即拒绝落盘**：题量不足 / 漏题 / 引用不存在的风险点编号 → 直接报错退出，绝不把半成品喂给下一个 agent。
- **零丢失**：JD 解析中未归类的行并入硬性要求并告警。
- **事实边界完整**：求职者的事实来源必须包含 claims 清单（见下方教训）。

**DoD**
- [x] 3 轮跑通，题目覆盖 JD 全部硬性要求维度（4/4：框架 / 中间件 / JVM / 稳定性）
- [x] 每条风险点至少被追问 1 次（12/12）
- [x] 中断后能从最后一轮继续（状态在 `rounds/state.json`；回归测试用例「中断后可从下一轮继续」）
- [x] 单次运行 ≤ 15 分钟、≤ 60 次模型调用（实测 13.7 分钟 / 6 次）

**真实运行记录**（`李岳临_简历.pdf` × 供应链履约 JD，`python pipeline/orchestrate.py check --root .`）

| 指标 | 实测 |
|---|---|
| 轮次 / 题量 | 3 轮 / 17 题 |
| 追问链 | 50 层（每轮 15 / 17 / 18 层）|
| 维度覆盖 | 4/4（框架 3 题、中间件 2 题、JVM 2 题、稳定性 2 题）|
| 风险点追问覆盖 | 12/12 |
| 模型调用 | 6 次（面试官 3 + 求职者 3）|
| 墙钟耗时 | 13.7 分钟 |
| 求职者示弱 | 主答中 8 题显式示弱，0 题「答不住」 |
| 主答长度 | 均 138 / 157 / 176 字 |

**P2 踩过的坑**

| 现象 | 根因 | 修法 |
|---|---|---|
| 求职者把简历里**真实存在**的 95% 拦截率、99.98% 准确率当成"面试官编的陷阱数字"拒绝认领 | 注入的「事实边界」被渲染截断（每段经历只给 3 条要点、每条截 100 字），候选人看不到这些数字 | 事实边界改为完整事实 + claims 清单（量化声明与机制声明全量注入）；修复后第 2 轮候选人主动认领并给出口径 |
| 第 3 轮主答偏长（均 176 字） | 提示词给了字数区间但无强制 | 已知偏差，交由 P3 评分时按"啰嗦"扣分项处理，不在 P2 硬卡 |

## P3 · 评估层 ✅

**产出**：`pipeline/score.py`（rubric 驱动评分器）、`pipeline/salary.py`（薪资建议）、
`pipeline/report.py`（三件套渲染）、`prompts/reviewer.md`（实装）、
`02_复盘报告.md` / `03_薪资建议.md` / `04_简历风险点.md`

**关键设计：把 rubric 变成会报错的契约**

评审 agent 产出的不是一个"分数"，而是一份**受脚本强校验的判分依据**。`score.py`
从 `rubric/scoring.md` 解析维度、权重、档位、硬性扣分规则，从 `rubric/red_flags.md`
解析 27 条雷区编号，然后：

| 强制项 | 实现 |
|---|---|
| 不得引入 rubric 之外的维度 | 维度集合必须与 rubric 完全一致，否则报错退出 |
| 无原话不扣分 | 每条扣分引用的原话必须是候选人答题文本的**逐字子串**（去空白归一化），改一个字就拒绝计分 |
| 先定档再微调 | 档位必须是 1–5 整数；题分 = 档位 + clamp(维度均分 − 档位, ±0.5)，落到 0.5 网格 |
| 硬性扣分覆盖分档 | `hard_rules` 显式声明，取值为 rubric 第 3 节的规则名（`编造`/`常识错误`/`矛盾`/`不确定`/`答不出`），规则名同样受 rubric 校验 |
| 聚合确定 | 加权总分 = Σ(维度均分 × 权重)，全部由脚本计算，评审只提供维度分 |

**DoD**
- [x] 评分严格来自 rubric 维度，每处分扣引用候选人原话（13 项契约/负向测试 + 真实 17 题逐条校验）
- [x] 同输入两次运行加权总分偏差 ≤ 0.3（**验收 A1：A 组 4.0 vs B 组 3.9，偏差 0.10**）
- [x] 薪资只输出区间 + 推理链 + 依据声明，无无出处数据（否定感知守卫拦截行情措辞）
- [x] 风险点全部带编号、类型、严重度、可验证性、改写建议（12 条；改写建议经"不新增数字"校验）
- [x] 02/03/04 编号引用闭环 100%（12/12 风险点被追问，`report.py --strict` 通过；01/05 属 P5 产出，全量闭环校验在 P5 补齐）

**真实评分结果**（A 组，`李岳临_简历.pdf` × 供应链履约 JD）

| 指标 | 值 |
|---|---|
| 加权总分 | **4.0 / 5**（大概率通过） |
| 分轮均分 | 第 1 轮 3.5 ／ 第 2 轮 4.0 ／ 第 3 轮 4.5（递增：越到后面越稳） |
| 维度均分 | 正确性 4.32 ｜ 深度 3.65 ｜ 一致性 4.15 ｜ **匹配度 3.15（最低）** ｜ 表达 4.29 ｜ 风险控制 4.65 |
| 雷区命中 | G-01×8、E-02×3、E-05×2、G-03×2、G-02×1、T-02×1、T-03×1；**F 类 0** |
| 薪资建议 | 26.0K–30.5K（中位 28.0K），定位分位 0.55，JD 区间 20K–35K |
| 评审调用 | 6 次（A/B 两组各 3 轮）+ 1 次改写建议 = 7 次 |

**A1 漂移的实际构成**：加权总分只差 0.10，但正确性维度差 0.35、第 3 轮题均分差 0.42——
B 组额外抓到了「Oracle 用 Binlog 同步」这条 M-01（A 组漏判）。这正是 rubric 第 5.5 条
要求的"锚点样例库"要解决的问题，已按真实案例新增 5 条样例（`rubric/scoring.md` §7）。

**P3 踩过的坑**

| 现象 | 根因 | 修法 |
|---|---|---|
| 评分器把所有 `risk_id` 判成非法编号 | `out/risks.json` 只在 `init` 时生成，而真实演练是在加了这行代码之前跑的 | `commit` 时幂等重写（已修），并从 `state.json` 补出该文件 |
| 命令成功却退出码 1，stderr 打出一整坨对象 | `sys.exit(main())`，而 `main()` 返回 dict | 改为 `main(); sys.exit(0)`，失败路径仍由 `die()` 抛 SystemExit |
| 薪资守卫把自己写的免责声明判成违规 | 黑名单匹配不区分语境，「未使用市场行情」里含「市场行情」 | 改为否定感知（词前 14 字内有否定语则放行） |
| 报告首行出现"# 复盘报告模板" | 模板的维护说明被当成正文渲染 | 模板说明改为 HTML 注释 |
| rubric §3「与自己简历矛盾 → 扣 1 分」无法表达，评审只能靠一致性维度近似 | 判分 schema 只有雷区编号，没有硬性规则字段 | 新增 `hard_rules`，取值同样受 rubric 校验 |
| 缺口题题分被抬高到 4.0（低匹配度只产生 −0.5） | 这是 rubric 的设计：缺口通过**匹配度维度**进入加权总分（本例匹配度 3.15 为最低项），题分只反映单题技术表现 | **不擅改规则**，固化为锚点样例 S-05 并说明理由 |

## P4 · 验真层（护城河）

**产出**：`pipeline/verify_evidence.py` → `evidence.json`

**功能**
- 量化声明 → git 统计比对
- 机制声明 → 代码 grep 比对
- 技术常识 → 领域规则校验（如 binlog 属于 MySQL）
- 四档判决：可信 / 存疑 / 与事实不符 / 无法验证
- **面试可见性分级（决定严重度）**：当场可判 / 追问可判 / 需材料才可判 / 不可判

**DoD**
- [ ] 能复现 `docs/EVIDENCE.md` 第 5 节的 7 条实证判断
- [ ] 每条结论附带可复现命令
- [ ] 只读，绝不修改被检查仓库
- [ ] 记录取证时点、分支、HEAD commit
- [ ] 无法验证的声明**不**被判为编造
- [ ] **严重度由面试可见性决定，不由 verdict 决定**：代码级不符（提交数 148 vs 150、
      测试数 111 vs 140、代码里搜不到某机制名）属"需材料才可判"，严重度降到 🟡/⚪，
      **不得直接判编造**；只有当场可判（Oracle 用 binlog）才给 🔴
- [ ] `04_简历风险点.md` 按可见性排序，"面试前必做"清单只收当场可判/追问可判两类

## 建议开发顺序

**P0 → P1 → P2 → P3（先跑通主链）→ P5（能出 PDF）→ P4（补护城河）→ P6（打包）**

理由：先让主链端到端可跑（哪怕没有验真），能最快验证"这套流程是否真的有用"；验真层虽然最有价值，但它是**锦上添花且实现成本高**的部分，放在主链跑通之后收益最大。
