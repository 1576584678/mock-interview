# 证据验真层设计（护城河）

## 1. 为什么这层最重要

模拟面试产品遍地都是，因为"用 LLM 出题 + 给建议"没有门槛。
**但"拿机器可验证的现实去核对简历"有门槛**：它要求系统能读 git 历史、扫代码、比对依赖清单，并判断"简历的说法与代码事实是否一致"。

这一层输出的不是"建议"，而是**会被面试官当场戳穿的清单**。这是用户真正会为之付费的东西。

## 2. 三类核对

### A. 量化声明 → git 统计

| 简历声明 | 核对方式 | 本次实证 |
|---|---|---|
| "累计 150 次提交" | `git log --author=<me> --oneline \| wc -l` | **148** |
| "主导某分支重构" | `git log --oneline <branch>` + 分支列表 | 148 次提交、229 全分支提交 |
| "历时 N 年/N 个月" | 首次/末次提交时间差 | 与简历时间线一致 |

### B. 机制描述 → 代码 grep

| 简历声明 | 核对方式 | 本次实证 |
|---|---|---|
| "Redis 队列 + 异步任务调度" | 搜 `RPUSH/LPOP/BLPOP` 与消费循环 | 实为 **List 轮询消费**（无阻塞消费语义） |
| "业务指纹判重/复活机制" | 搜 `fingerprint` / 指纹相关标识 | **不存在 → 编造** |
| "三级幂等键" | 搜实体字段与唯一索引定义 | 真实存在（任务/计划/步骤） |
| "平台级熔断" | 搜 Resilience4j 配置与拦截器位置 | 真实存在（挂在 HTTP 客户端拦截器层） |

### C. 技术常识 → 领域规则

不需要读代码，仅靠常识判断即成立：

| 简历声明 | 常识判定 |
|---|---|
| "Oracle 用 Binlog 同步" | **Oracle 没有 binlog**（binlog 是 MySQL 概念） |
| "Kafka 消费者并发 = 分区数" | 错；RabbitMQ 没有分区概念 |
| "60 秒自动半开" | 需核对 Resilience4j 的 `automaticTransitionFromOpenHalfOpenEnabled` 默认值 |

## 3. 可验证性分级（每条风险点必须标注）

| 级别 | 含义 | 处置 |
|---|---|---|
| **可验证** | 有代码 / git / 依赖清单直接证据 | 立即修正，最高优先级 |
| **可佐证** | 有间接证据（分支名、依赖、日志） | 建议修正或补充口径 |
| **仅叙述** | 只能靠候选人自述（旧项目、已离职公司） | 标注"未验真"，给出话术防守建议，**不判定为编造** |

**关键原则：不能把"无法验证"当作"造假"。** 旧项目无法取证的声明只能提示风险与话术，绝不能扣分或贴上编造标签。

## 3b. 面试可见性（第二轴，决定严重度）

> 这一轴来自一次真实的用户判断：**"有些东西面试官看不到，所以不算作假"**。
> 代码级不符（提交数 148 vs 150、测试数 111 vs 140、代码里搜不到某个机制名）
> 在面试现场**不可能被验证**——面试官不会拉你的仓库。它不该与"Oracle 用 binlog"
> 这种当场就能戳穿的硬伤同级。

| 可见性 | 含义 | 典型例子 | 严重度 | 处置 |
|---|---|---|---|---|
| **当场可判** | 领域常识错误，面试官无需任何材料就能发现 | 「Oracle 用 Binlog 同步」「RabbitMQ 消费并发=分区数」 | 🔴 一票否决 | 暴露基础不牢，信任崩塌，必须改 |
| **追问可判** | 面试官深挖 1–3 层细节必然崩 | 「Redis 队列」实为 List 轮询；机制名说不出失败路径 | 🟠 高 | 决定技术深度评价，必须准备 |
| **需材料才可判** | 只有索要仓库/要求现场演示才会暴露 | 150 vs 148 次提交、111 vs 140 个测试、代码里存在某机制与否 | 🟡 中→⚪ 低 | **建议改成真实数字**（因为它影响你敢不敢让对方看仓库），但**不判编造、不改变面试结论** |
| **不可判** | 旧项目、已离职公司，任何人都无法取证 | 「某系统 QPS 3000」无内部数据 | ⚪ 低 | 只给话术，禁止判定 |

**两条由此推出的铁律：**

1. **F 类编造的判据是"面试中说了不存在的东西"，不是"代码里搜不到"。**
   代码级不符只有在**候选人在面试中复述了该机制并讲错**时才升级为编造——
   判定依据是面试实录，不是 grep 结果。
2. **严重度 = 可见性优先，一致性其次。**
   「与事实不符 + 需材料才可判」比「存疑 + 追问可判」轻。前者是数字对不上，
   后者是当场就要崩。

**对比：一次真实的误判修正**

| 声明 | 代码结论 | 我最初的判定（错） | 修正后 |
|---|---|---|---|
| 累计 150 次提交（实测 148） | 与事实不符 | 🟠 高（数字不实） | 🟡→⚪ 需材料才可判：改成 148 即可，面试结论不变 |
| 业务指纹判重/复活机制 | 代码中不存在 | 🔴 F-01 编造 | 🟡 需材料才可判：**除非面试中讲错**，否则不算编造 |
| 111 个单元测试（实测 140） | 与事实不符 | 🟠 高 | ⚪ 需材料才可判，且实际是**往少了写**，无收益 |
| Oracle 用 Binlog + Kafka | 与事实不符 | 🔴 | 🔴 维持：当场可判，常识级硬伤 |
| Redis 队列 + 异步任务调度 | 存疑（List 轮询） | 🟠 | 🟠 维持：追问可判 |

## 4. 实现要点（P4）

```python
# 输入：resume.json（量化声明 + 机制声明清单）、repo_path
# 输出：evidence.json
{
  "claims": [
    {
      "id": "C-03",
      "type": "quantitative",          # quantitative | mechanism | tech_common_sense
      "text": "累计输出 150 次提交",
      "method": "git log --author",
      "observed": "148",
      "verdict": "与事实不符",          # 可信 | 存疑 | 与事实不符 | 无法验证
      "visibility": "需材料才可判",     # 当场可判 | 追问可判 | 需材料才可判 | 不可判
      "severity": "⚪",                # 由 visibility 决定，不由 verdict 决定
      "evidence": "git log --author=liyuelin --oneline | wc -l = 148",
      "confidence": 0.95,
      "is_fabrication": False          # 只有面试实录里讲错，才由评审层置 True
    }
  ]
}
```

**约束**：
- 只读操作，绝不修改被检查的仓库。
- 作者名/时间范围需向用户确认（不同邮箱可能指向同一人）。
- 每条结论必须附带**可复现的命令**（用户能自己验证）。

**P4 新发现（不在原 7 条里）**：
- **E-11 分库分表 → 存疑**：一次性误判为"可信"，原因是 `shard` 命中了一个 `requestedShardCount` 字段

  后改判**存疑**——这正是"证据要能自证，不能靠关键词像"的教训。
- **E-08 平台级熔断 → 可信**：实据是 `http-client-interceptor/pom.xml` 里的 `io.github.resilience4j` 依赖
  （此前一次命中是**注释掉的** `new CircuitBreaker(...)` 行，已加"注释不算证据"规则）。

**⚠️ 一处数字更正**：此前手工统计"140 个 `@Test`"是**粗计数**（`Select-String -Pattern '@Test'` 会把

两者相差 2 处，全部是注解前缀误计——**以 138 为准**。

## 5b. 对报告的影响

- `04_简历风险点.md` 的严重度列必须按可见性排序，而不是按"是否与代码不符"排序。
- 严重度为 ⚪/🟡（需材料才可判）的条目，改写建议写成
  「改成你能当场说清的数值」，**不写"准备更正话术"**——面试官不会问，问了也只是换个数字。
- 只有 **当场可判 / 追问可判** 的条目才进入"面试前必做"清单。

## 6. 不做什么

- ❌ 不分析代码质量（那是 code review 的职责）。
- ❌ 不做能力断言（"他其实不会并发"）——只判断**表述与事实是否一致**。
- ❌ 不把证据外传：所有分析在本地执行，只有结论进入产物。
