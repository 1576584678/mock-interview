# 项目规划

## 1. 定位

一个 **DSH Skill**，把"模拟面试 + 简历体检 + 薪资判断"固化成可重复执行的流程。

**目标用户**：正在准备面试的开发者（首发自带技术岗模板，尤其是后端 / 分布式方向）。
**使用姿态**：单机、本地、不依赖外部服务；输入是文件，输出是文件。

## 2. 目标与非目标

### 目标
- 让候选人**在上场前知道自己会被问什么、哪里答不住、哪句话会被戳穿**。
- 让简历的每一句量化声明都有出处或口径。
- 给出**可解释**的薪资判断，而不是一个孤立数字。

### 非目标（明确不做）
- ❌ 不做"替你写经历"。Skill 只能让真实经历表达准确。
- ❌ 不做实时市场薪资数据库（无合法稳定数据源，做不到就诚实地不给）。
- ❌ 不做线上 Web 服务 / 用户系统 / 支付（在 P6 之前不考虑）。
- ❌ 不做通用聊天助手；它不是"AI 陪你聊天"，是**有交付物的流程**。

## 3. 差异化：为什么不是又一个 AI 模拟面试

市面同类产品（牛客、面试鸭、各类 GPTs 工作流）的输入只有**简历 + JD**，因此它们能做的只有"按 JD 出题 + 给建议"。

本项目的第三输入是**可验证的现实**：

| 验证手段 | 能查出什么 | 本次实证 |
|---|---|---|
| `git log` 作者维度统计 | 提交数、时间线、分支活跃度 | 150 次提交 → 实测 148 |
| 代码 grep | 机制是否真实存在 | "业务指纹判重" → 不存在 |
| 技术常识校验 | 张冠李戴的组件 | "Oracle 用 Binlog" → Oracle 无 binlog |
| 结构统计 | 测试/模块规模声明 | 111 个单测 → 实测 140 |
| 依赖清单（pom/package.json） | 技术栈声明是否属实 | Spring Cloud 组件真实在用 |

**护城河不在"面试对话"，在"验真 + 定向改写 + 话术联动"这个闭环。**

## 4. 架构总览

五层，每层输入输出都是文件（JSON / Markdown），任一环节可单独重跑：

```
L0 输入层    resume.pdf/docx/md  →  parse_resume.py  →  resume.json
             jd 文本            →  parse_jd.py      →  jd.json
             代码仓库路径        →  verify_evidence  →  evidence.json

L1 分析层    resume.json + jd.json          → 匹配矩阵 / 缺口清单
             resume.json + evidence.json    → 风险点清单（带可验证性分级）

L2 演练层    interviewer.md + candidate.md  →  rounds.json / 对话实录

L3 评估层    rounds.json + rubric/*         →  scorecard + 复盘报告
             resume.json + jd.json + evidence → 薪资建议
             resume.json + 风险点            → 改写建议

L4 产出层    templates/*                    → 五件套（md / csv / html / pdf）
```

详见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 5. 阶段划分与工作量

| 阶段 | 内容 | 工作量 | 依赖 |
|---|---|---|---|
| **P0** | 骨架与契约 | 0.5 天 | — |
| **P1** | 解析层：简历/JD → 结构化 JSON | 0.5–1 天 | 无 |
| **P2** | 演练层：双 agent 多轮编排 + 状态落盘 | 1 天 | P1 |
| **P3** | 评估层：评分 / 薪资 / 风险 | 1–2 天 | P2 |
| **P4** | 验真层：代码 + git 交叉核对 | 1–2 天 | P1 |
| **P5** | 产出层：HTML/PDF + 报告渲染 | 0.5 天 | P3 |
| **P6** | 打包：安装说明、示例、README | 0.5 天 | 全部 |

**自用可用版（P0–P3+P5）≈ 3.5–5 天；含验真层的完整版 ≈ 5–7 天。**

## 6. 验收标准（量化，不达标不算完成）

| # | 标准 | 阀值 |
|---|---|---|
| A1 | 同一输入两次运行的加权总分偏差 | ≤ 0.3 |
| A2 | 风险点中"可验证类"（有代码/事实依据）占比 | ≥ 40%（有代码路径时） |
| A3 | 一次完整运行耗时 | ≤ 15 分钟 |
| A4 | 一次完整运行模型调用次数 | ≤ 60 次 |
| A5 | 五件套一致性：每条简历改动都可回溯到风险点编号 | 100% |
| A6 | 编造检出率（人工标注的故意埋雷） | ≥ 80% |

A6 的测试方法：准备 3 份含已知编造的测试简历作为回归集，每次改 prompt 后重跑。

## 7. 关键决策记录（ADR）

| # | 决策 | 理由 |
|---|---|---|
| ADR-1 | 用**双 agent**（面试官 / 求职者）而非单 agent 自问自答 | 双 agent 逼出真实的追问链；单 agent 会自我迎合 |
| ADR-2 | 评分用**固定 rubric + 分档锚点**，不用模型自由打分 | 自由打分两次跑差异可达 1 分以上，无法验收 |
| ADR-3 | 薪资**只给区间 + 推理链**，不给单点值 | 模型无实时市场数据，给单点值就是编；宁少不给错 |
| ADR-4 | 验真层**可选但优先** | 无代码仓库时可降级为纯文本判断；有代码时是唯一护城河 |
| ADR-5 | 产物固定五件套、固定文件名 | 可对比、可回归、可作为 Skill 的稳定交付契约 |
| ADR-6 | 简历修复先出 HTML，用户确认后才转 PDF | 不可逆变更需人工闸门（来自真实使用反馈） |
| ADR-7 | 优先无第三方依赖的 Python 脚本 | 环境可控，少一个装不上的包就多一次失败 |

## 8. 商业化判断（诚实版）

| 形态 | 价值 | 变现能力 |
|---|---|---|
| 自用工具 | 高（且开发成本近零） | — |
| 开源分发 | 口碑价值，提升个人技术影响力 | 无直接收入 |
| 产品化售卖 | 需求真实但赛道拥挤；客单价低、复购极低（拿到 offer 就走）、获客贵 | 仅在"验真层 + 垂直岗位模板"上存在差异化机会 |

**结论：先做自用 + 开源。把它当作面试作品与能力证明，而不是创业项目。** 如果将来看到明确的付费信号（例如用户愿意为"简历验真 + 定向改写"付费），再考虑产品化。

## 9. 验收结果（实测，P6 收口）

| # | 标准 | 阈值 | 实测 | 结论 |
|---|---|---|---|---|
| A1 | 同一输入两次运行的加权总分偏差 | ≤ 0.3 | A 组 4.0 ／ B 组 3.9 → **偏差 0.10**（分轮偏差 0.20/0.17/0.42） | ✅ |
| A2 | 风险点中"可验证类"占比（有代码路径时） | ≥ 40% | 12 条中 **可验证 8 条（67%）**（可佐证 1、仅叙述 3） | ✅ |
| A3 | 一次完整运行耗时 | ≤ 15 分钟 | 单轮墙钟 3.0 分钟（P2 DoD 自检），3 轮 ≈ 9–10 分钟 + 脚本渲染 < 1 分钟 | ✅ |
| A4 | 一次完整运行模型调用次数 | ≤ 60 | 示例（3 轮）**8 次**；真实跑（P2+P3 全量）**17 次** | ✅ |
| A5 | 五件套一致性：每条简历改动可回溯到风险点编号 | 100% | `verify_links.py --strict`：**悬空 0、孤岛 0、未进 04 为 0** | ✅ |
| A6 | 编造检出率（人工标注的故意埋雷） | ≥ 80% | 3 份回归简历埋雷 1 处（B 的 "Oracle 用 Binlog"）→ **检出 1 处（100%）**，A/C 无误报 | ✅ |

A6 的测试方法已自动化：`tests/check_resumes.py` 直接断言「B 的埋雷必须被 E-01 以"与事实不符 / 当场可判 / 🔴"检出，
且 A、C 不得误报」，改 prompt / 改规则后重跑即可。

**运行成本实测**（示例 `examples/minimal/`，3 轮 16 题 46 层追问）：
模型调用 8 次（面试官 3 + 求职者 3 + 评审 1 + 改写 1），其余全部由确定性脚本完成。
示例实测：加权 **4.1/5**、薪资区间 **25.5K–30.0K**（中位 27.5K，JD 20–35K）、
A5 闭环 **100%**、验真层无仓库时 **编造判定 0**。
